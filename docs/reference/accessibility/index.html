Reference / Accessibility

Dostępność

Komponenty są projektowane z natywną semantyką i wzorcami klawiaturowymi. Dostępność aplikacji nadal zależy od poprawnego HTML, etykiet, treści i integracji. Nie deklarujemy pełnej zgodności WCAG bez audytu całej aplikacji.

01 / FOKUS

Widoczny stan klawiatury

Motyw stosuje wspólne :focus-visible z kontrastową obwódką. Nie usuwaj jej w aplikacji. Po zamknięciu menu lub dialogu przywróć fokus do wyzwalacza.

02 / FORMULARZE

Natywne kontrolki

Input, Select, Textarea, Checkbox, Radio i Toggle korzystają z natywnych elementów. Łącz je z label; radio grupuj fieldset i legend. Błędy opisuj tekstem oraz aria-invalid/aria-describedby. Kolor nie zastępuje opisu.

03 / WIDOKI

Tabs i postęp

Tabs wymagają powiązań tablist/tab/tabpanel, roving tabindex i strzałek. Natywny progress wymaga etykiety, a Segments użyte jako skala postępu powinny mieć role="progressbar" i aktualne aria-value*. Wartość pokazuj także tekstowo.

04 / WARSTWY

Menu, dialog, tooltip

Menu wymaga synchronizacji aria-expanded, strzałek, Home/End, Escape i zwrotu fokusu. Dialog używa natywnego showModal(), nazwy przez aria-labelledby i sensownego fokusu początkowego. Tooltip ma wyłącznie treść pomocniczą powiązaną przez aria-describedby; istotne informacje muszą być widoczne także na dotyku.

05 / NOWE KONTROLKI

Disclosure, Range i Breadcrumbs

Disclosure używa natywnych details/summary oraz atrybutu open. Range jest etykietowanym input type="range" z natywną obsługą klawiatury i disabled. Breadcrumbs wymagają nazwanego nav, listy ol/li oraz aria-current="page"; dekoracyjne separatory CSS nie mają znaczenia dla czytnika.

06 / KOMUNIKATY

Notice i Toast

Statyczny Notice może być zwykłą treścią. Dynamiczna informacja używa role="status"; role="alert" tylko dla pilnych błędów. Toast ma ręczny przycisk zamknięcia i nie znika w trakcie czytania.
